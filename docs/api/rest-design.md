# REST Design

Theory answers and design decisions for the REST API of the mail system. The contract itself is `openapi.yaml`.

## 1. REST Fundamentals

### 1.1 Check Your Understanding

**Q1. Resources and representations: B and C**

- B is correct. A resource is an abstraction. The same email can be shown as a short summary in a list, as a detailed JSON document, or as a different format.
- C is correct. The URI names the resource (`/emails/{emailId}`), the HTTP method says what to do with it (`GET`, `PUT`, `DELETE`).
- A is wrong. A resource is an abstraction of an entity, not a table. An email resource can combine data of several tables (email, metadata, attachment metadata).
- D is wrong. REST does not prescribe a media type. Our API also uses `application/problem+json` and binary content.

**Q2. Stateless communication: B**

- B is correct. Every request carries what the server needs to understand it (token, path, body). The server may still use the persistent resource state, for example the stored email.
- A is wrong. Stateless means the server keeps no client-related memory between requests (no session). Data is still stored persistently in the database.
- C is wrong. The server must not rely on a previous request that "selected" an email. The email is named in every request by its URI.

**Q3. Safety and idempotency: B and D**

- B is correct. Idempotency is about the effect on the server, not about the response. The second `DELETE` of an email may answer `404`, but the server state is the same as after the first.
- D is correct. That is the definition.
- A is wrong. `GET` must be safe (no side effects). Sending an email changes state, so it must not be a `GET`.
- C is wrong. The `PATCH` method does not guarantee idempotency. A patch that appends a recipient changes the result with every repetition.

**Q4. Responses and API contracts: A and C**

- A is correct. `201 Created` plus `Location` points to the new resource.
- C is correct. `204 No Content` has no response body.
- B is wrong. `202 Accepted` only says the request is accepted for processing, not that the work succeeded.

### 1.2 Explain and Apply

**1. PUT versus PATCH.** `PUT` replaces the whole resource with the sent representation. `PATCH` changes only some attributes.

- Idempotent partial update: `PATCH {"subject": "Final report"}`. Repeating it leaves the same subject.
- Partial update whose repetition changes the result: "append `x@y.de` to `cc`" (for example a JSON Patch `add /cc/-`). Every repetition adds another entry.

**2. Classification.**

| Method | Safe | Idempotent (guaranteed by the method) |
|---|---|---|
| GET | yes | yes |
| POST | no | no |
| PUT | no | yes |
| PATCH | no | no (not guaranteed) |
| DELETE | no | yes |

The guarantee belongs to the method, the behavior belongs to a concrete operation. A `PATCH` that sets a field is idempotent in behavior, but the method does not promise it. A `POST` can be idempotent in behavior if the server rejects duplicates, as our transmission does (a second send of a sent email gives `409`). A `DELETE` is idempotent even though the repeated request answers `404` instead of `204`. Note: the lecture slide lists `PATCH` as idempotent; the HTTP specification (RFC 5789) does not guarantee it, so this document does not rely on it.

**3. Numeric IDs versus UUIDs.** Numeric IDs are short, readable, and ordered, but they are generated by the database, so an entity must be saved before it has an ID, they can collide when several databases are merged, and they can be guessed by counting up (`/emails/24`). UUIDs can be generated anywhere without coordination and cannot be guessed, but they are long and hard to read. We use UUIDs.

**4. Overfetching and underfetching.**

- Overfetching: the mailbox overview returns the complete content (up to 100 000 characters) and all attachment metadata of every email, although the list only shows sender, subject, and status. Much more data is sent than needed.
- Underfetching: the overview only returns IDs. To show subject and attachment count the client needs one more request per email (and one more for the attachment metadata). Many small requests replace one.
- Our design: a short `EmailSummary` for the list (with `attachmentCount`) and an `EmailDetail` for one email.

## 2. OpenAPI Contract

`openapi` is the version of the OpenAPI specification that the document follows. Tools read it to know how to parse the file. `info.version` is the version of our own API contract (`1.0.0`). It changes when our API changes.

## 3. Path Design

| Operation | Method and path |
|---|---|
| Create | `POST /emails` |
| List | `GET /emails` |
| Read | `GET /emails/{emailId}` |
| Update | `PUT /emails/{emailId}` |
| Delete | `DELETE /emails/{emailId}` |

**PUT or PATCH?** Only `PUT`. An update must keep the email valid (at least one recipient, non-blank subject and content). With `PUT` the client sends the complete writable representation, so the server validates exactly the same rules as for creation. `PATCH` would need merge rules, especially for recipient arrays (replace, append, remove), and would allow an invalid intermediate state. `PUT` is also idempotent by definition. The mail form edits the whole email anyway. `PATCH` answers `405`.

**Theory: `GET /deleteEmail?id=42` and `POST /updateEmail`.**

- `GET` must be safe. A delete behind a `GET` can be triggered by link prefetching, crawlers, or caches. Both paths put a verb into the URI and the identity in a query parameter or the body, so the URI does not identify a resource.
- `POST /updateEmail` hides that the operation is an idempotent replacement and gives the client no resource URI.
- Alternatives: `DELETE /emails/42` and `PUT /emails/42`.
- HTTP semantic requirements (safe `GET`, idempotent `PUT` and `DELETE`, meaning of status codes) are rules of the HTTP specification. URI naming conventions (nouns, plural, lowercase, hyphens) are agreements for consistency. HTTP would not reject `/deleteEmail`, but a `GET` that deletes violates the HTTP semantics.

## 4. Request and Response Schemas

**Required, optional, server-controlled.**

| Kind | Fields |
|---|---|
| Required when writing | `subject`, `content`, and at least one address in `to`, `cc`, or `bcc` |
| Optional when writing | `from` (defaults to the current user, must equal it if given), `to`, `cc`, `bcc`, `replyTo` |
| Server-controlled | `id`, `createdAt`, `updatedAt`, `sentAt`, `status`, `source`, `attachments` |

**Recipient rule.** `anyOf` with three alternatives: `to` present with `minItems: 1`, or `cc` present with `minItems: 1`, or `bcc` present with `minItems: 1`. Requiring only `to` would reject emails with only `cc` or `bcc`. The rule was tested against the schema with valid and invalid examples.

**Limits** (from `domain.md`): subject 1 to 255 characters, content 1 to 100 000 characters (both with at least one non-whitespace character), at most 50 addresses per list, address at most 254 characters.

**Rules that need server-side validation in addition to the schema:**

- `from` equals the address of the current user.
- Total of `to`, `cc`, and `bcc` is at most 100 addresses.
- Addresses are unique ignoring upper and lower case (the schema only finds exact duplicates).
- The email exists, belongs to the current user, and is not `sent` (state rules).
- Attachment limits: count, total size, and the real size of the received bytes.
- Whether an address is deliverable.

**Omitted, empty, and null values.** Omitted optional lists mean empty lists. Empty lists are allowed if another list has an address. Explicit `null` in a request is rejected with `422`. In responses an unset `sentAt` is an explicit `null`. With `PUT`, omitted optional properties are reset to empty, so the result is always the complete representation and always valid.

**Server-controlled fields in requests.** The request schemas have `additionalProperties: false`, and the server rejects such requests with `422` and a pointer to the property. It does not ignore them silently, so a client notices its mistake. `readOnly` annotations are not used for enforcement.

**Attachment metadata** has `id`, `fileName`, `mimeType`, and `size` in bytes. The storage path is never exposed.

**Theory.**

- Request and response representations differ from persisted domain objects because the API must not expose internal data (password hashes, storage paths, internal IDs), because a client must not write server-controlled data (mass assignment), and because the API should stay stable when the database changes. Creation needs no ID and no timestamps, responses need them.
- A mailbox summary differs from the detailed response to avoid overfetching: a list does not need the content and the attachment metadata of every email.
- Passwords and password hashes never appear in user responses. A password is only needed as input. A leaked hash allows offline guessing, and the lecture points out that exposing the password is not allowed.

## 5. Operations as Resources

Sending is modeled as a **transmission** resource:

- `POST /emails/{emailId}/transmissions` performs one send attempt.
- `GET /emails/{emailId}/transmissions` lists the attempts, `GET /emails/{emailId}/transmissions/{transmissionId}` reads one.

The collection is plural because one email can have several attempts (an `error` email can be sent again).

**Why not set `status` to `sent`?** Status is server-controlled. Writing the field would only claim that the email was sent. Nothing would be transmitted. Sending is an action with an outcome that can fail, so it needs its own resource.

**Processing model: synchronous, `201 Created`.** The server performs the attempt during the request, so the result is known when it answers. `201` is chosen because a transmission resource is created, with a `Location` header. `202 Accepted` would fit an asynchronous model, which we do not use.

**Effects.**

| Outcome | `status` | `sentAt` | `updatedAt` |
|---|---|---|---|
| `succeeded` | `sent` | time of the attempt | time of the attempt |
| `failed` | `error` | unset | time of the attempt |

The project statuses `draft`, `sent`, and `error` are kept. There is no extra "sending" status.

**Rules.** An `error` email can be edited and sent again. Sending an already `sent` email (and a received `extern` email) is rejected with `409` before an attempt starts. Such a rejection changes nothing and creates no transmission.

**Timeout and retry.** `POST` is not idempotent by definition, but the operation is safe to repeat: once an attempt succeeded the email is `sent` and every further request gets `409`, so the email cannot be sent twice. After a timeout the client reads the transmissions or the email first and repeats the request only if the email is still `draft` or `error`. The server handles attempts for one email one after another. The method gives no guarantee, our operation behaves safely.

**Theory.** A successful HTTP exchange only means the API request was processed. The external mail server can still refuse the message. That is why a failed attempt is answered with `201` and `outcome: failed`. As a resource, the transmission can be read later, so the client can inspect the outcome and the history of attempts without sending again.

## 6. Pagination and Scalable Data

- **Page-based** pagination: `page` (zero-based, default 0) and `size` (default 20, maximum 100). Page-based is simple for a mailbox UI with page numbers.
- **Empty result:** `200` with an empty `data` array, `totalElements: 0`, `totalPages: 0`. A page beyond the last page is also an empty `200`.
- **Ordering:** `createdAt` descending, tie-breaker `id` ascending. Without a stable order, the database may return rows in a different order per request, so successive pages could repeat or skip emails.
- **Response:** `EmailPage` with `data`, `page`, `size`, `totalElements`, `totalPages`.
- **Filters:** `status` (`draft`, `sent`, `error`) and `source` (`intern`, `extern`). Both are combined with AND and are applied before pagination, so the page numbers refer to the filtered result.
- **Invalid values** (for example `size=0`, `page=-1`, `status=foo`) answer `400`.
- Examples for a page of drafts and a page of received emails are in the `200` response of `listEmails`.

**Theory.** Pagination limits how many items are returned. Filtering (selection) chooses which items are returned. Projection chooses which attributes are returned. Our design supports pagination and filtering. It has no projection parameter, but the fixed `EmailSummary` is a built-in projection. Pagination alone does not prevent overfetching of fields: every item of a page would still contain all fields. That is why the list returns summaries.

## 7. Error Codes and Error Responses

All errors use the schema `ProblemDetail` (`application/problem+json`, based on RFC 9457) with `title`, `status`, `detail`, `instance`, and optional `errors` with a JSON pointer per field.

| Case | Status | Reason |
|---|---|---|
| Malformed JSON | 400 | The request cannot be parsed. |
| Invalid pagination or filter value | 400 | A malformed request parameter. |
| Unsupported request media type | 415 | The body type is not `application/json` (or `multipart/form-data` for uploads). |
| Missing recipient, empty subject or content, unknown or server-controlled property | 422 | Well-formed JSON that violates schema or business rules. |
| Unknown email | 404 | The resource does not exist. |
| Email of another user | 404 | Same answer as an unknown email, so the API does not reveal that it exists. |
| Modify a `sent` email | 409 | Valid request, but the current state forbids it. |
| Send an already `sent` email | 409 | Same reason. |
| Unsupported HTTP method | 405 | With an `Allow` header that lists the supported methods. |
| File or attachments too large | 413 | The upload exceeds the limit. |
| Missing or invalid token | 401 | The user is not identified. |
| Unexpected error in the server | 500 | Not caused by the client. It can happen in any operation, so every operation lists it. The body never contains internal details (stack trace, SQL, file paths). |

**Transmission failures.** A request rejected before an attempt (`404`, `409`) is an error response. An accepted attempt that fails is not an API error: it is `201` with `outcome: failed`. This follows from the synchronous model.

**Success codes.** `200` for reads and updates with a body, `201` when a resource is created (email, transmission, attachment) with `Location`, `204` for deletes (no body), `202` is not used because there is no asynchronous processing.

**Theory.**

- Repeated `DELETE` requests need not return the same status. Idempotency means the same effect on the server. The first delete answers `204`, the second answers `404`, and the server state (no email) is the same.
- `400`: the request is syntactically wrong. `404`: the resource is unknown. `405`: the method is not supported for this path. `409`: the request conflicts with the current state. `415`: the request media type is not supported. `422`: the content is well-formed but semantically invalid.
- Our API uses all six, as in the table above, and additionally `500` for unexpected server errors. We keep `400` for syntax and query parameters and `422` for body validation, so clients can tell "could not be understood" from "understood but not acceptable".

## 8. Attachment Upload and Download

| Operation | Method and path |
|---|---|
| Upload one file | `POST /emails/{emailId}/attachments` |
| List metadata | `GET /emails/{emailId}/attachments` |
| Read metadata | `GET /emails/{emailId}/attachments/{attachmentId}` |
| Download bytes | `GET /emails/{emailId}/attachments/{attachmentId}/content` |
| Delete | `DELETE /emails/{emailId}/attachments/{attachmentId}` |

The `/content` sub-resource separates the file bytes from the metadata.

**Upload representation:** `multipart/form-data` with one part named `file`. File name and MIME type come from the part headers (`Content-Disposition`, `Content-Type`), and the server counts the size while receiving. A file name in JSON alone would not transmit a file. The server returns them as `AttachmentMetadata`.

**Limits:** file 1 byte to 10 MB, all attachments of an email at most 25 MB, at most 10 attachments. Too large: `413`. Wrong upload media type: `415`. Attachment count exceeded or invalid file name: `422`.

**Download:** binary body. `Content-Type` carries the stored MIME type, `Content-Disposition: attachment; filename="..."` carries the file name, `Content-Length` the size.

**Several attachments:** the client repeats the upload. Workflow: `POST /emails` (draft), `POST .../attachments` for the first file, `POST .../attachments` for the second file, `GET /emails/{emailId}` shows both in `attachments`.

**No update.** To replace an attachment the client deletes it and uploads the new one. Both are only possible while the email is `draft` or `error`. For a `sent` email, upload and delete answer `409`, so the read-only rule holds.

**Deleting an email** permanently removes all its attachments.

**Theory.**

- A nested URI alone does not prove that an attachment belongs to the email. The server must check that the attachment belongs to the email in the path and that the email belongs to the current user. Otherwise the answer is `404`.
- Bytes and metadata are different representations: metadata is small JSON that is listed and cached cheaply, the bytes are large binary content that is streamed.
- JSON is not suitable for file content because binary data would need base64 (about one third larger), the complete file must be held in memory and parsed, streaming is not possible, and the MIME type is lost.
